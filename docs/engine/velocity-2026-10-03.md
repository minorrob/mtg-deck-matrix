# Engine build velocity — how to build the remaining mechanics and cards faster (2026-10-03)

Rob asked (2026-10-03): *"Evaluate a reliable and trusted approach for how we can speed up the creation of these
mechanics. Anything at universal variables or underlying mechanics that we can solve and then tag to the different
card mechanics or similar?"* This is the evaluation, written after batches 79 and 80 (#573, #574). The same content is
Rob's page at claude.ai/artifact/AJwY6vA1CkeYrokbSZC85b; this file is the copy the repository keeps.

**Recommendation.** Two tracks, measured first. Most of the remaining cards need a definition, not a mechanic: write
those in bulk from Oracle text through the checks the repository already has. For mechanics, build the universal
variables (axes) once in the engine's core, so every effect gains them together, instead of one card's form at a time.

## Where the most-played cards stand (batch 80)

Of the 3,238 most-played Commander cards (`docs/engine/coverage.md`):

| | Cards |
| --- | ---: |
| Defined and playable today | 992 |
| Every mechanic built; only the definition is missing | 1,275 |
| Still need at least one mechanic the engine lacks | 971 |

A batch defines about nine cards (batch 78: 10, 79: 9, 80: 3 plus 3 corrected). At that rate the 1,275 cards that need
only a definition are about 140 batches. That band is the largest single opportunity, and it is definition work.

## Track A — definitions in bulk

Oracle text is heavily templated. A drafter that maps Oracle phrases to the engine's grammar can draft definitions for
the 1,275 in bulk, reading Oracle text and the Comprehensive Rules only — never Forge's scripts (ADR-001).

What makes a draft trusted: the schema and `checkFidelity` (the definition says what the card says); a smoke game per
card, as the card loader runs; scenarios generated from templates by kind (an enters trigger, an activated ability, a
removal spell), run through the real rules; a second, independent derivation before a provisional definition is
promoted (`game/tools/engine-ingest.mjs` already stores session-written definitions as provisional); and every card that
fails becomes a measured backlog item with its reason. Start with a 50-card pilot to measure the pass rate and the
kinds of errors before scaling to 50–100 cards a batch.

## Track B — axes, not cards

Build every axis once, in the dispatcher and the binding layer (`game/engine/script/effects/index.mjs`,
`script/bind.mjs`, `script/resolution.mjs`), so every primitive gains it at the same time:

- **Who** — you, each player, each opponent, a target player, that player
- **How many** — an amount on every number, X included
- **From where** — a zone, the top N, among what was remembered
- **Who chooses, and how** — "may", any number, at random, an order the player picks
- **Memory** — remember, "that many", "that card", "this way"
- **Duration and condition** — until end of turn, until your next turn; if, as long as

The proof standard does not change: a suite per axis, deliberate breaks, the 1,463 scenarios as a regression net.

## Measure first

The inventory (`game/tools/engine-inventory.mjs`) already records some Forge option names per card, as names and
counts only. Extend it to every effect's parameters, map each to an axis, and let the catalog's "What to build next"
rank axes by the cards they unlock. It closes the blind spots found while building — an order the player chooses
mid-effect (Scroll Rack), planeswalker loyalty (Tezzeret), "exiled with this" (Nautiloid Ship), transform (Fable of the
Mirror-Breaker), attaching a chosen permanent as an effect resolves (Armored Skyhunter), a spell's own "when you cast
this spell" (Kozilek). The random order was another; batch 80 built it.

## Risks, and how each is held

| Risk | How it is held |
| --- | --- |
| A drafted definition that looks faithful but plays wrong | fidelity, smoke game, templated scenarios, a second derivation, provisional until promoted |
| An axis made general changes how existing cards behave | every scenario and suite on each axis change; breaks prove each guard |
| A decision made for a player that the rules leave to them | each choosing axis offers the choice to its owner; automatic only where the rules leave none, cited |
| Something counted as built that is not | parameter-level measurement; a failing draft names the missing thing |
| Forge's implementation creeping in | the drafter reads Oracle text only; the inventory keeps names and counts, never script text |

## The order of work

1. **One measurement batch** — parameter-level inventory, the axis matrix, the catalog ranking axes. No new cards.
2. **A 50-card bulk-definition pilot** from the cards with every mechanic built; report the pass rate and error kinds.
3. **Alternate** — an axis batch, then a bulk-definition batch, so each new axis is turned into cards at once.

Estimates, not measurements: at 50–100 cards a batch, the 1,275 are 13–26 batches instead of about 140. The pilot
replaces this estimate with a measured rate.
