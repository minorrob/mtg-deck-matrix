## Batch 1 — the table's size and shape

| # | What Rob said | State |

### What was wrong

`max-height:72vh` on a box carrying `aspect-ratio:4/3`. **A height cap on a fixed-ratio box caps
its width as well** — the box shrinks in both directions to honor the ratio. On a tall window the
table stopped well short of the content column while the panel below it ran the full width, which
is exactly what the screenshot showed. The ratio was worth keeping; the cap was not.

The card had a second, separate version of the same mistake: `width:min(28%,320px)` stopped it
growing once the table passed 1143px, so on a wide screen it shrank against its own seats.

### What it is now

The table is `width:100%` and `4:3`. A 2×2 grid divides both dimensions, so **every quadrant is
4:3 at any size** — seats keep their shape as they grow, with no rule of their own. The card is
`width:30%` with `aspect-ratio:4/3`, so it carries a seat's shape and scales with the table.

Measured at 1600×950, against the live host:

| | width | height | ratio |
|---|---|---|---|
| main | 1369 | — | — |
| table | 1297 | 973 | 1.333 |
| a seat | 647 | 484 | 1.335 |
| the card | 389 | 291 | 1.333 |

The seat went from about 460 wide to 647.

**One thing this surfaced:** giving the card `overflow:auto` turned the decorative wand-and-gear
stamp — which is meant to bleed off the bottom-right corner — into a scroll region, and the card
grew two scrollbars. It is `overflow:hidden` now, so the stamp is clipped by the card's own
corner, which is how wireframe 2b draws it.

### Guards left behind

Three checks in `tests/wireframe-conformance.mjs`, all red before the fix:

- *the table is not height-capped, which would cap its width* — fails on any
  `max-height:<n>vh|vw|px` in the base `.cm-lobby-table` rule while it carries an aspect-ratio.
- *the table's card carries a seat's aspect ratio* — reads both ratios out of the sheet and fails
  if they differ by more than 0.02.
- *the table's card scales with the table* — fails on a `min(%, px)` width, which is the shape of
  the bug that capped it.

### 3.1 — the sea was moving all along

Measured in the Playwright Chrome: **60 rAF ticks a second**, field moving. It was not *visible*.

Two false leads worth recording. The in-app browser pane reports `document.hidden = true` and
fires **zero** rAF callbacks, so a frozen canvas there proves nothing — the same shape of trap as
the ServiceWorker error. And the design files do specify the animation: `screens/table-sea.js` is
the designer's own implementation, and our `crankmagic-sea.js` is a faithful port of its palettes
and field function. **Nothing needed to go back to the designer.**

The README says why it was faint, under "Play lobby (table-first, wireframe 2b)": the element runs
at **"~80% opacity under a dark top/bottom gradient"**. The build ran it at 50% with no gradient at
all, so the only way to keep words readable was to dim the whole element — moving, at half
strength, everywhere. The gradient is 2b's own layer, `.cm-seat-shade`.

### 4.1 / 4.2 — a fixed ratio cannot fit a window

`aspect-ratio:4/3` makes height follow width and nothing else, so on a wide window the table ran
past the bottom of the screen and never answered zoom. It takes the height actually left below it
now, measured per render. A quadrant's shape therefore follows the window's, which is what he
asked for. **No scroll** was the choice between his two options: a table you scroll to see is a
table you cannot read as a table.

One catch found by measuring: `crankmagic-online.js` inserts the host-offline banner **above** the
table after this view has drawn, pushing it ~190px down while it kept a height measured from where
it used to be — overflowing by exactly the banner's height. The room is observed now, not measured
once.

Verified at five window shapes, all **FITS**: 1920×1080, 1600×950, 1400×900, 1280×800, 1100×700.

### 4.6 — the table could never have started

`startReady` required `o.seat && o.ready` for every AI seat. **Ready Up is a control on your own
seat**, and an AI has no one to press it — and every deck apply sets `opp.ready = false`, so
changing a deck actively made it worse, exactly as he found. The table waited on a flag nobody at
it could supply.

Readiness for an AI is a fact about its deck, not a record of a click: `L.seatReady` says a seated
AI whose deck passes the table's checks is ready. The flag still governs the host and human
guests, who really do press it. The status pill uses the same verdict, so the table cannot read as
waiting while the gate is satisfied.

### 5.2 — the table never started itself

The README describes a table that does: *"There is no Launch button: the table starts itself with
the 10 s countdown once all four seats report ready."* Nothing in the lobby ever counted or
launched — `canStartSoon` produced a sentence and that was all. Rob has now also asked for a Start
button, which supersedes the README on that point.

The launch row is two columns: the reading, and Start at `minmax(64px,22%)`. The countdown runs ten
seconds and writes its own seconds **straight into the text element** rather than through a redraw
— a redraw a second would rebuild the table, restart four canvas animations and drop focus out of
whatever the host was using. It begins by itself the moment the table is ready, and Start begins it
at any time.

**A loop I put in and caught before merging:** `cancelCountdown` redraws, the redraw asks
`syncCountdown` again, and a table that was still ready started counting straight back up — so
Stop did nothing. An explicit stop is remembered until readiness is lost or Start is pressed.

### 5.3 — the menu had no background because it had no tokens

Every design token is declared on `#matrix-v2` (`crankmagic-design.css` lines 19, 21, 45). The menu
was appended to `document.body`, **outside that element**, so every `var(--v-*)` in `.cm-menu`
resolved to nothing. Custom properties inherit down the DOM; a popover paints in the top layer but
still inherits from its DOM parent. It is appended inside `#matrix-v2` now — `rgb(45, 40, 35)`,
measured.

### 5.6 — two dead controls, one of them invisible

- **Game history** set `location.hash = "reports"`, and there is no `reports` view. `route()` falls
  back to `decks` for any hash it does not know, so the control *looked* like it worked and landed
  on the wrong page. It opens a history dialog built from `C.state.games` now.
- **Bracket and Game Changer cap did nothing at all.** They were bound with `addEventListener`
  straight after `C.main.innerHTML = …` — correct when they lived in a panel on the page, useless
  once they moved into a menu, because a menu's markup only enters the DOM when it opens, long
  after that binding has run and found nothing. They use the document-level change delegation now,
  which does not care where a control is or when it arrived.

**Binding at render time is the wrong shape for anything that appears later.** That is the general
lesson and it is in `docs/INDEX-where-things-live.md`.

The permutation pass grew to **15 checks** and now covers the menu (paints with tokens, every
control wired, toggles closed), the launch row, and Game history.

| # | What Rob said | State |

### 6.3 — the loop was mine, and it buried the evidence

`lobby-start`'s catch set `startInFlight = false` and redrew; the redraw asked `syncCountdown`;
the table was still ready, so it counted down into the same failure again, for ever. **A loop that
retries a failing call without limit is worse than one that stops, because it buries the message
that would explain it** — which is exactly what happened to the 404.

Now: one go and one more (`START_ATTEMPTS = 2`), then the launch box states the error and the
button becomes **Send Log**. The held error carries the message, the time, the route, the seat
count and the bracket, so the mail is worth sending. Pressing Start or the table losing readiness
clears it, so a fixed problem can be tried again.

### 6.2 — what the 404 is not

Ruled out by reading and then by driving: every path the lobby calls exists in
`game/tools/serve-review.mjs`, and that file's `/api/` block (line 107) **always** replies with a
JSON body — while `lobbyApi` only falls back to the literal `"HTTP 404"` when a response has no
body and no statusText. So it is not an API route. The reproduction never reached a start attempt
(the probe seats one player, and the table needs two), so the actual request is still unknown.

**Send Log exists so the next occurrence explains itself** rather than being reasoned about from a
screenshot.

### Found while reproducing: a host route that could never answer

`/api/desktop-deks` is a **GET**, and it sat *below* the catch-all guard
`if(req.method!=='POST'||…) return reply(403)`. Every non-POST request was rejected before reaching
it, so the route answered 403 to the only method it accepts, and **the host's real `.dek` decks
never reached the lobby**. The lobby's call is wrapped in a try/catch with an embedded fallback, so
it failed silently and looked like a preference.

Moved above the guard, keeping the token check the other privileged GETs use. Verified on the
running host: **403 without a token, and D1–D7 with one.**

## Batch 7 — the 404, explained by Send Log in one line

Rob's Send Log carried this:

```
HTTP 404
Route: https://minorrob.github.io/mtg-deck-matrix/#game
```

**He was on GitHub Pages.** `fetch('/api/setup')` resolved to `https://minorrob.github.io/api/setup`,
which does not exist — a bare 404 with no body, exactly what the message implied. And from an
`https` page, reaching `http://127.0.0.1:8768` is **mixed content**, which browsers block outright,
so Play on Pages cannot start a game at all, ever.

Send Log was built one batch earlier precisely so an unexplained failure would explain itself.
It did, on its first use, and it cost one line of reading instead of a session of guessing.

### The defect is not the 404

**The Play tab on Pages looked completely operational.** The banner in `crankmagic-online.js` was
gated on `location.hostname === '127.0.0.1'`, so on every origin that *cannot* play it never
appeared: the table rendered, the seats seated, the countdown ran, and the first thing that told
anyone anything was an HTTP status code.

Now:

- A page served from the web and a host that is not running are **different problems** and get
  different words. The remote case reads *"Games run on your own computer"* and explains where to
  go; it has no **Check again** button, because there is nothing to retry.
- The lobby **will not count down when nothing can answer** (`hostReachable`). Counting toward a
  call that cannot succeed is what produced the 404 in the first place.
- Pressing Start on such a page says what to do instead of failing: *"A game is played by
  CrankMagic Online on your own computer, and this copy cannot reach it. Open
  http://127.0.0.1:8768/ there to play."*
- `lobbyApi` no longer reports `"HTTP 404"`. The host always answers with a JSON body, so a
  response without one did not come from the host — and the message now says so, naming the origin.

### Driven, not assumed

A local server cannot reproduce this, because `127.0.0.1` and `localhost` are both local by
definition. **`tools/lobby-remote-origin.mjs`** serves the repository from disk under
`http://crankmagic.example` by fulfilling every request in the browser, with `/api/*` returning
404 — a real page on a real remote origin as far as the app is concerned.

```bash
GEOMETRY_REQUIRED=1 node tools/lobby-remote-origin.mjs
```

Result: banner *"Games run on your own computer"*, no Check again, and Start explaining itself.

### 8.1 — `â—□ Checking CrankMagic Onlineâ€¦`

UTF-8 bytes shown as Windows-1252. **Windows PowerShell 5.1 reads a `.ps1` as the system ANSI
codepage unless the file starts with a byte order mark**, and `launch-crankmagic-online.ps1` had
**five** distinct non-ASCII characters (`● … ✕ ⚠ ✓`) and no BOM. Rob saw only the first because it
is the first status the dialog shows; `✓` `✕` `⚠` were all broken too.

The BOM is the fix rather than stripping the glyphs — `✓ ✕ ⚠` carry meaning at a glance in a box
that is mostly status. But a BOM is invisible and any editor that rewrites the file without one
puts the mojibake straight back, so **`tests/script-encoding.mjs`** holds it: any `.ps1` carrying
non-ASCII must begin with a BOM. Verified through PowerShell itself — it now reads `U+2026`, the
real ellipsis, where it read three mojibake characters before.

### 8.2 — reading order

Seat 1 top-left, then 2, 3, 4. This **supersedes the README**, which reads *"in the order they sit
(2 · 3 / 4 · 1, you bottom-right)"*.

The change is four lines and no CSS, because `.cm-q-XX` names a quadrant's **inner corner** — the
one touching the table's card — rather than its position. The mapping is the mirror of the
position, so every rule keyed on those classes kept working untouched. That is the whole reason
they are named that way.
