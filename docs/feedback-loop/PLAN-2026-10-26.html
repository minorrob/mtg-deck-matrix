The feedback loop: from any page to a fix in production, and a thank-you back

Every person in every access group can report a bug or ask for an enhancement from wherever they are, including mid-game. The report lands in CrankMagic's own storage with enough metadata to act on, an agent turns it into a Linear issue and a recommendation for Rob, Rob approves from wherever he is, a session executes and ships, and the person who asked gets an email with a link when it is live.

Two principles hold the loop together. Nothing leaves CrankMagic's own storage without a record: the report is a row in D1 before anything else sees it, and every later step writes its state back to that row (issue id, approval, PR, release, notified). Rob approves, agents propose: no issue is executed without his word, and his word is recorded on the issue, not in an inbox.

1 · Capture: one control on every page and in the game

Today "Send feedback" is a mailto: link in crankmagic-app.js with no metadata. It becomes a control in the app shell (a glyph in the header, per the symbols-first rule) and in the board's rail during a game. One press opens a small sheet: what happened (free text), what kind (bug or enhancement, two glyphs), an optional screenshot (the browser's own capture of the page, where supported, else an upload), and Send. Everything else is gathered by the sheet, not typed.

The schema is CrankFeedback@1, bounded by construction (text 2,000 characters, screenshot 1 MB as WebP, console lines 20), validated by a suite, and shared between the sheet and the Worker.

2 · Store: a Worker route and a D1 table

CrankMagic already runs on Cloudflare Workers and D1 with signed-in people behind Access. Adding a store there costs one migration and one route; adding Supabase would add a second vendor, a second identity and a second place secrets live. Recommendation: D1, not Supabase.

  • POST /api/feedback: any signed-in person, any group; rate-limited to 10 an hour a person; the screenshot stored in R2 under the row's id when R2 is on, else dropped with a note on the row.
  • GET /api/admin/feedback?since=&state=: the owner, and the triage agent with a service token (an Access service token for the agent's application, never a person's session).
  • PATCH /api/admin/feedback/:id: the agent and the release workflow write state: new → triaged → approved → in-progress → released → notified, with the Linear issue id, PR number, release commit and the notification's message id.
  • Migration: feedback table with those columns; the number is the next free one at build time (the engine lane numbers migrations).

3 · The triage agent

Runs on GitHub Actions in this repository on a schedule (hourly, and on demand), as the card-load and game-log compile workflows already do; it needs no server of its own. It is a Claude Agent SDK script on Claude Haiku 5.5 by default (Rob's lowest-cost rule), with the repository checked out so it can read the code the report points at.

  1. Reads rows in state new through the admin route with its service token.
  2. Groups duplicates (same route, same build, similar text) and links them to one issue.
  3. For each group: classifies bug or enhancement, picks the lane from the charter's file table (docs/program/README.md §3) by the route and files involved, sets a severity (1 blocks play, 2 wrong result, 3 friction, 4 wish), drafts a title in Rob's wording style and a body with the reproduction, the metadata and the files it believes are involved.
  4. Creates the Linear issue in the matching project under the north star, with the Lane label and a new feedback label, and writes the issue id back to the rows.
  5. Writes a digest: one line per issue with its recommendation (fix now, batch, decline with a reason), and sends it to Rob by the route in section 4.

The agent never executes a fix. Its only writes are Linear issues and the feedback rows' state.

4 · Approve: the email is optional, Linear is the record

Rob asked for an email with the recommendations he can reply to, or better, for it to come straight to Claude or Codex on his phone. Both are built on one mechanism: approval is a label on the Linear issue (approved, declined, or a comment with changes). Everything that reads approvals reads Linear, so it does not matter where Rob was when he decided.

  • Email digest (Resend, through cloud/mail.mjs, sender already set up): each line links to its Linear issue. Rob approves by tapping through to Linear, or by replying with the issue keys and a word. Replies are read by the same hourly workflow through a Gmail label, parsed for issue keys and approve, decline or change, and applied as labels and comments. Reply parsing is kept simple on purpose; ambiguous replies become a comment on the issue and a line in the next digest.
  • Straight to Claude on the phone: the digest is also delivered as a scheduled task that opens a Claude Code cloud session with the digest as its prompt (create_trigger with create_new_session_on_fire), so Rob opens the app and the recommendations are waiting with the code in reach. Approving there is the same Linear label, applied by the session.
  • Codex and GPT on the phone read Linear directly; no second channel is built for them.

Skipping the email entirely: turn off the digest email once the scheduled session proves itself. The loop does not depend on it.

5 · Execute and ship

An approved issue is picked up by whichever session Rob is in, or by a scheduled execution session, one issue per branch named by lane (claude/engine-feedback-<key>, codex/workshop-feedback-<key>). The session follows AGENTS.md as it stands: branch, fix, a test that goes red under a break, tools/local-ci.sh, a draft PR naming the Linear issue and the feedback ids, ready when green, merged on one green run, staging by the engine lane's release owner, production on Rob's go. Linear moves with it: in progress on the branch, in review on the PR, done on the merge. Nothing in this step is new process; the loop plugs into what the repository already does.

6 · Notify the person who asked

When production is released (tools/release-production.sh already records the commit), a step in the release workflow asks the Worker which feedback rows reached state released by that commit (the PR's feedback ids, carried in the merge commit's message), and sends each reporter one email through Resend: thank you for the feedback; what was fixed or added, in one plain sentence from the issue's title; a link to crankmagic.com at the page they reported from. The row moves to notified with the message id, so nobody is thanked twice and the owner's admin view shows who was told what. A reporter who sent five reports fixed in one release gets one email listing them.

Rob's calls

  • decision D1 over Supabase for the store, and GitHub Actions over a hosted runtime for the agent (section 2 and 3). Both keep the stack to what already runs.
  • decision Approval by Linear label as the record, with email and the scheduled phone session as two ways to set it.
  • decision Which Linear project feedback issues file under: the outcome project the route maps to (default), or one "Feedback" project with the lane label.
  • decision Screenshots: keep them (R2) or drop them until R2 is on.
  • decision The sender for reporter emails: the invite sender already configured, or a new feedback@ address.
