## 5. How a wave is run (the procedure this session used)

**One wave = four session workers + one integration.** Each worker runs in its own git worktree, defines its list,
commits locally and reports. The integrator cherry-picks the lanes, resolves conflicts, verifies the whole and
opens one PR.

**1. The brief.** `docs/handoff-2026-10-12/BRIEF-wave.md` is wave 4c's brief. Change its base commit, its timing
gate's path and its "added these" list for the next wave. Each worker's prompt names its lane, its theme and its
cards, most-played first, and tells it to read the brief. `game/tools/batch/README.md` is the procedure each worker
follows.
- **Timing gate.** While the integrator verifies on the same machine, workers must not run suites:
  `engine-room-games` has a 45-second budget that load can break. Workers wait for a file to say "passed".

**2. Integrating.**
- Cherry-pick each lane's commits onto the branch, in lane order.
- Generated files conflict every time. Run `docs/handoff-2026-10-12/regen.sh <checkout>`. It:
  - takes ours of `definitions.mjs`, `coverage.md`, `catalog.md` and `engine-catalog.json`;
  - regenerates them with `engine-definitions` / `engine-coverage` / `engine-catalog --write`;
  - sets the README's suite count;
  - checks the data inventory. If it has drifted, run `node tools/data-inventory.mjs` to write it.
- `README.md` conflicts: `docs/handoff-2026-10-12/resolve-readme.py README.md` keeps ours for the count line, and
  both sides for each suite's list entry.
- Code conflicts: keep both sides. **When two lanes built the same rule, keep one implementation.** 4b's CR 305.6
  was built three times. Then retarget the other lanes' breaks to the one kept.
- **Break anchors.** Run `python3 -I game/tools/batch/anchors.py`. It reports every break whose anchor a merge moved.
  - Re-anchor each on the code it was written for, by exact line replacement. Never by counting parentheses: that
    corrupted two breaks files once.
  - Prove each one caught: `python3 docs/handoff-2026-10-12/break-one.py <file> <label>`.

**3. Verifying the integrated head.** All of these, before the PR is marked ready:
- `node --stack-size=4000 game/tools/batch/check-cards.mjs`: 0 failed.
- The suites, four at a time, with the list built as in `docs/handoff-2026-10-12/README.md`:
  `bash docs/handoff-2026-10-12/run-list-at.sh <checkout> <out dir> $(cat list)`.
  - The list is `tests/engine-*`, `room-*` (minus `room-resolve-all`), `table-basics`, `game-*`,
    `commander-pilots*`, `pilot-policy*`, `data-integrity`, `feature-wiring`, `generators*` and `advisor`.
  - **Run them again after any fix commit.** A late fix can move the data inventory, which only `generators` checks.
- The seeded games, all with `--replay --leaks`:
  - `node --stack-size=4000 tools/fuzz-live.mjs --library --humans 0 --seeds 1-10 --replay --leaks`
  - `... --library --humans 0,1 --seeds 11-20 ...`
  - `... --backup <Rob's v43 backup> --decks "D1 Tymna + Kraum|D3 Kiora|D5 Teysa Karlov|D6 Krenko" --humans 0 --seeds 1-10 ...`
  - All must be clean.
- `bash tools/local-ci.sh HEAD 0`: the scan. Actions' `suites` run is the gate.

**4. The PR and the merge.**
- Open a draft PR from `claude/admiring-franklin-58cxy4` and add the standing comment: the two Workers Builds checks
  fail by design on every branch but `release/pages`.
- `suites` runs only once the PR is marked ready. Mark it ready when the local proof is in.
- On a green `suites`, merge with a merge commit, giving the head's SHA.
- Then restart the branch from main: `git checkout -B claude/admiring-franklin-58cxy4 origin/main`.

**5. Releasing to staging** (after each merge; staging only; production only on Rob's go):

```
WRANGLER=<wrangler.js> bash tools/release-staging.sh <a checkout of main> <work dir>
CLOUDFLARE_ACCOUNT_ID=<id> bash docs/handoff-2026-10-12/verify-staging.sh <work dir> <previous version id prefix>
NODE_USE_ENV_PROXY=1 node tools/staging-check.mjs --expect <main sha>   # signed in; run again if the CDN still serves the old one
```

`verify-staging.sh`:
- waits for Workers Builds to deploy the new version;
- compares the deployed `play-worker.js` with the release's `wrangler deploy --dry-run` bundle, byte for byte;
- lists the AI bindings.

It only reads from Cloudflare. A Cloudflare API token must be available to curl.
