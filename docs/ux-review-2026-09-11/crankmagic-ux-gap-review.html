CrankMagic · minorrob.github.io/mtg-deck-matrix · walkthrough 2026-09-11

UX gap review

Every view was driven in Chrome against the live six-deck library (My Decks, each deck page, Insight and Manage menus, Collection, Shop Acquisition and Assembly, Discover, Deck Lab, Edit definition, Log a game, Reports), then re-run headless at 1440 and 390px with geometry measured, and cross-checked against the repo source (crankmagic-collection.js, crankmagic-decks.js, deck-page.js, crankmagic.css, BACKLOG.md). Findings are ranked by what they cost on a build night or a store run, not by effort.

Core use cases the app is judged against

Use caseWhat Rob is doingExpected pattern
UC1 BuyFinish six 100-card decks inside a hard budget ($100 pool, nothing over $30, per-deck cap $225), local store before TCGplayer, price-verified before money moves.A shopping list with a price on every line, a running total, per-deck and per-vendor subtotals, a one-tap "bought / ordered" that records what was paid.
UC2 OrganizeKeep a 100% accurate record of what is physically in each deck box versus the bench, and assemble boxes at the table.A per-deck pull sheet grouped by where each card is right now (this box · bench · another box · ordered · to buy), with a tick that writes back.
UC3 DefineSix definitions with Base / Tuned / Max tiers, at most two Game Changers, an Upgrade Path of "X replaces Y for $Z because".Upgrades visible on the deck page as replace-pairs with tier, price and reason, promotable in one action.
UC4 UpdateReport card events fast, often from a phone at Game Theory or CCS: bought, ordered, arrived, moved, replaced X with Y.Primary action on the row, not in a 14-item menu; same columns and actions on phone and desktop.
UC5 Spend vs performanceKnow what each deck cost, its value against the cap, and whether it wins.Cost basis and market value per deck, a game record that is read back (W-L, win %, $ per win) on the deck page.

Priority scale

P0 Fundamental gap in flow: a core use case cannot be completed in the app.   P1 Significant UX/UI improvement: the use case works but costs real time or errors.   P2 Consistency and clarity.   P3 Visual micro-adjustments (spacing, alignment, wrapping).

P1

4 · Orders: capture per order, never per card

UC1 Buy · UC4 Update

Actions → Mark Ordered opens an inline stepper (◀ 1 ▶ ✓) and records nothing about the order. The first draft of this review proposed a capture dialog per line; Rob rejected it, correctly: nobody fills in 85 screens. Price capture therefore moves off the line entirely.

  • Zero-screen default. Marking a row Ordered or Bought stamps the catalog price as paid. No dialog. Totals and cost basis work at sheet-price accuracy, which is what the v11 math already uses.
  • One dialog per order. Tick rows (the tick column exists), press Ordered… once: vendor, order ref, shipping, expected date. Shipping is spread across the lines. Eighty-five cards, one screen.
  • Paste the receipt for exact prices. Import list already has an ordered mode and a paid column mapping; add "Paste order confirmation" that parses the TCGplayer / Game Theory email, matches names to To buy rows and overwrites the stamped price in one commit. Optional, and the only place real prices are ever typed.
  • Arrival is one click on the order row.

13–14 · Scroll reset and deep-link timing

all

Navigating from a scrolled Collection to a deck page lands at the deck page's bottom (SWOT panel) because the router does not reset scrollTo(0,0) on view change. Opening #decks?deck=deck:live:D3 in a fresh tab before the repository has resolved renders "Unable to open this view · Deck not found. Reload and try again." The route should wait on the repository promise and render a skeleton, then the deck.

P2

15–16 · Placeholder copy and phone wrapping

UC3 · UC4

All six tiles say "Mechanic to explore" because definition.mechanics is empty in live-load.json; populate it (Spirit tribal · Tokens · ETB, Proliferate · Poison, …) from the strategy tags the guide already derives, and render nothing when empty. On the 390px Store view, Price cells wrap "$0.6 / 9" and card names break mid-word ("Beast Wit hin", "Blood Art ist") because the compact table applies letter-spacing and allows breaks anywhere. Price needs white-space:nowrap and a fixed 56px column; names need overflow-wrap:normal; word-break:normal.

19–20 · Button system and filter alignment

visual

Measured: .v-button 43px (padding 10px 15px, 14px text, 21px line-height, radius 8), .cm-text-button 29px (4px 0), .cm-tile-menu-btn 36px (1px 6px). Rows that mix them (tile footers, deck action row, table Actions cells) have no shared vertical center. .cm-actions gap is 10px while the text inside buttons has 15px side padding, so the gap between two buttons reads tighter than the gap between a button's edge and its own label. The chevron glyphs in "Insight ▾", "Manage ▾", "User Functions ⌄" are typed characters that sit 2px below the baseline.

22–23 · Deck page stat row, banner, and the rest

visual

The stat row uses grid-template-columns:repeat(auto-fit,minmax(112px,1fr)) across 1330px, so five figures sit ~230px apart with the label in 12px lowercase; the eye has to travel to compare 72 with 55. Cluster the figures (finding 2's layout) with 26px gaps and sentence-case labels. The "Finalized: reservations track what this list needs…" banner shows on every deck page with no dismiss and no state change behind it; make it a one-time tip with a close button, or fold it into the readiness strip's tooltip. Composition chart: zero-height bars still print "0" above the "0" axis label; hide the value label when it is 0. Sidebar footer "Your cards. Your library." uses three font sizes in five lines; set one size (12px) and one color. "Group: D3 Atraxa Proliferate" is an underlined link inside a chip while the two chips beside it are static; either all three are links or the group chip becomes a plain chip with a separate "Open group" text button.

Confidence, by layer

Structure of the ranking (P0 items are the ones that block UC1 and UC2): high. Each was reproduced in the live app and confirmed in source. Individual mock-ups: medium; they are one reasonable layout each, drawn to the app's existing tokens, and the first build night will move some fields. Micro measurements (px values in 17–21): taken from computed styles at 1440×900 and are exact for that viewport. "Final" here means final until the pull sheet and the priced buy list have been used at a table and at a store once.
