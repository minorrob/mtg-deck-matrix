# CrankMagic — acceptance and branch completion

**An Intelligent MtG: Commander Deck Creator & Card Libary**

7 September 2026 · final proposed release gates · production execution awaits sign-off.

This is the verification contract for the [full proposal](improvement-plan.md), [collection workflow](collection-workflow.md) and [simulation plan](simulation-fidelity-plan.md). The final HTML is a temporary sample-data design study. Its browser checks validate the preview interactions, not future production functionality or real-game prediction.

## What will count as complete

The static app supports the approved journeys below without inventing holdings, losing printings, hiding owned choices, silently weakening constraints or presenting unsupported measurements as reliable predictions. The release runs locally after its public assets are cached, exports user-controlled backups and workbooks, and needs no application server, framework or build step. UMD modules remain testable from Node; browser work runs in bounded workers.

The first supported simulator release must play four actual lists through the same legal-action authority and publish its coverage/policy/version information. A calibrated-human claim has an additional evidence gate: sufficient real-game data and prospective validation. If that evidence is unavailable, rules-tested simulation and logging can be completed, but human calibration remains explicitly unfinished. Passing application tests is not a substitute.

## End-to-end journey matrix

| Journey | Expected result and important boundary |
|---|---|
| First use with empty storage | No owned copies or orders exist until explicitly recorded. Sample/example decks are clearly separate from personal holdings. |
| Select Commander → Auto-build 99 | Name search or mechanics/EDHREC rank filtering produces an explicit commander choice. Dropdown shows name, color identity and a 1–3 word core mechanic; multiple secondary tags remain searchable. Rank is dated popularity, not power. Missing/stale rank, no results, offline search and filter clearing are handled. User intent constrains the remaining 99 (98 for legal two-command-zone configurations); filters never silently change a selection. |
| Commander name → deck | Local/alias lookup, supported public name lookup, then link fallback; identity/printing/rules provenance remains visible. AI guesses cannot establish legality. |
| Link → supplemental catalog | Resolve supported public endpoints; preserve an unresolved name/link as unverified if resolution fails. Reload, backup/restore and workbook export preserve the supplemental record without creating a holding. |
| Commander choice vs Deck Definition | All legal commanders are searchable regardless of holdings; unowned selection does not create ownership. Commander mechanics/rank narrow the catalog; Deck Definition controls the whole deck. Commander purchase contributes to budget. Help moves behind a keyboard/touch accessible ? window. |
| Run progress | Six stable labels, one active blue-flame indicator, completed green Forest indicators, pending neutral states and text equivalents. Run freezes validated inputs; real events drive production advancement. Cancel, errors, unsupported coverage and infeasible constraints never create false success. Reduced motion and pause preserve status clarity. |
| Report → compare → completed cards | Persist exact run/deck/protocol snapshots; reload restores history. Compare input changes separately from measured outcomes and flag incompatible protocols. Storage failure is visible and never says Saved. Completed Deck opens that result's Collection filter; clearing it shows everything. No inventory or reservations are created until explicit confirmation/finalization. |
| Roster facets and column choice | Type/subtype/mechanic/color/cost/mana/source/status/deck/bench/Sell-Trade facets intersect correctly. Hide Source, show Color, sort/group, use row Actions, clear filters and export without changing records. Columns stay aligned with headers, group spans adapt, and mobile overflow remains within the table. Missing metadata remains explicit. |
| Existing list → Lab | Choose a Collection group or create one by CSV, pasted text or individual cards. Count, identity, color identity, singleton exceptions, command zone, legality and bracket rules are separately validated. |
| Collection group organization | Adding the same copy to two ordinary groups keeps one copy. Moving a draft entry changes organization, not acquisition. A deck group action invokes actual slot/allocation review. |
| Import owned cards | Preview original rows, mapped fields, exact printings, quantities, conflicts and import mode. Malformed/fractional quantities are rejected without rounding/defaulting. Repeating an accepted batch adds nothing. |
| Finalize a new plan | Exactly 100 legal slots: link compatible owned copies/orders, create only unmet To buy requirements, and preserve the selected commander configuration. An empty library stays zero Owned. |
| Incremental acquisition | Mark ordered, receive and buy in store change the correct source quantities. Receipt is idempotent and does not claim In deck placement. Partial receipts preserve the outstanding order quantity. |
| Put in deck | Destination is explicitly selected. Matching reserved copy changes to In deck without changing Owned. A different/full deck requires reviewed slot replacement and donor effects. Archived destinations are absent. |
| Correct a mistaken status | Owned → Ordered/To buy previews the inventory correction and clears invalid physical placement while preserving the requirement. Undo restores the entire operation; a real return/cancellation is separately recorded. |
| Replacement → release | Accept/reject individual swaps or atomic synergy bundles. Release an outgoing owned copy to a compatible committed need, otherwise Bench; preserve physical origin until moved. Orders remain orders. |
| Several destinations need one copy | Deterministic visible priority, user destination override and Keep on bench are respected. One copy fulfills one requirement; printing constraints and deal holds are not relaxed silently. |
| Protected donor choice | Every owned copy remains visible. In deck/locked donors have named hard warnings. Transfer this copy, Acquire another and Keep current remain choices. A per-copy override does not unlock the whole donor. |
| Bench-focused optimization | Own current deck stays the tuning baseline; additions respect explicit bench/reserved/ordered/purchase/Sell / Trade scopes. Enabling In deck donors affects proposals only, never silently moves copies. |
| Stale recommendation acceptance | Recheck deck, copy, price/budget and allocation revisions. A card sold, moved or received since the run cannot be double-used. Recompute or resolve conflicts before commit. |
| Deck tile → overview → cards | Mechanic is below the commander; readiness badge is separate. Overview shows the correct full commander card and About the Commander beside Composition, with a compact stats/type/mana-symbol bullet, prominent keywords, ability bullets and a practical use statement. Triggered and activated abilities are distinguished. Preserve colors, strategy/how-to and labeled SWOT. View deck cards sets an explicit Collection filter; Clear filters shows all records. |
| Archive → reuse → restore | Preserve saved list/history; release only its allocations, fulfill compatible needs or Bench, retain orders and physical move tasks, remove obsolete purchase demand. Restore as draft and revalidate current availability. Undo does not overwrite intervening changes. |
| Sell / Trade designation | Select exact owned printings/quantities. Membership keeps Owned unchanged and visible to the builder; pending deals exclude automatic reuse. Completing a disposition changes only confirmed copies and exposes deck shortfalls. |
| Incoming trade | Agreement is non-owned future fulfillment, receipt creates only the actual received copies, and the requirement is not duplicated in purchases. Cancel/correct with history. |
| Shop in both views | Buying & orders and Ready to assemble share stable table columns, source/placement labels, filters, sorting and Actions. Receipt or placement can remove a row from the current filter without deleting its Collection record. |
| Discover graph | Typed, explained links; card/mechanic navigation, inspector, trail/back, pan, cursor-centered wheel zoom, keyboard/touch alternatives. Wheel outside the graph scrolls the page normally. Candidate selection preserves allocation context. |
| Copilot recommendations | Existing guide/graph/simulation capabilities remain available. Distinguish structural relationships, measured intervention, personal evidence and AI prose. Show costs, availability, alternatives and actionable affected cards without invented deltas. |
| Glossary definitions | All consumers read the same canonical term IDs and definitions. Dotted underlines, no hover reflow, above/below placement, mouse exit, focus/Escape, touch toggle and scroll dismissal work. Ambiguous noun/action terms stay distinct; product navigation is not auto-annotated. Revised definitions invalidate older caches and regenerate exports. |
| User Functions | Replace the top-right text/theme picker with the shared menu. Preserve backup export/import, Load default, Undo last load, Reset picks and Clear all data; add Excel export. Confirm scopes, preserve recovery snapshots and distinguish reset picks from collection deletion. Clear offers a backup, requires separate confirmation, touches only app-owned data and stays empty after reload. |
| Full backup and restore | All copies, printings, groups, orders, commitments, deck versions, supplemental catalog, logs, intent and evidence round-trip. Validate schema/checksum/quantities before replacement; corrupt input or quota failure leaves current state intact. |
| Excel export and edited re-import | Export enriched metadata and typed quantities with stable IDs, frozen/filterable headers and revision provenance. An independent reader verifies fidelity. Edited imports detect concurrent conflicts and never treat omitted filtered rows as disposals. |
| Offline, reload and interrupted save | Essential local workflows and file export work offline after asset availability. Show failures honestly, recover an interrupted transaction, preserve migration rollback and report file-mirror permission loss. |
| Concurrent tabs | Atomic revisions and conflict resolution prevent stale tabs overwriting newer holdings or consuming a copy twice. |
| Undo and audit | Compound transfers, replacements, archive and corrections reverse together when safe. History names the event and affected copies, including any conflict requiring reconciliation. |
| Optional AI fails or is disabled | Local app and deterministic explanations remain usable. No calls per simulation/action/iteration. Invalid references are rejected, usage caps enforced, sensitive records omitted unless deliberately selected. |

Test the defining invariants underneath these journeys: physical copies are conserved across reservations/transfers; received and disposed quantities account for ownership changes; plans never assert receipt; one copy cannot occupy two physical decks; a reserved order cannot be treated as available stock; archived destinations cannot receive allocations; all page projections agree at the same revision.

## Simulation correctness and evaluation gates

Use small authoritative positions for exact rules and complete supported pods for game behavior. Do not validate a numerical formula by writing a test that repeats that same formula. Test known counterexamples, conservation properties, independently derived expected states and the decisions a user would inspect in a replay.

| Gate | Required checks |
|---|---|
| Facts and provenance | Oracle/printing distinction, active face, variable characteristics, mana symbols, source/version hashes and deck/rule/opponent identities survive all hydration paths. |
| Opening and resources | Multiplayer free first mulligan and first draw, valid colored/colorless mana payment, exclusive resource consumption, commander tax/access and legal sequencing. |
| Rules transitions | Correct zones/object identities; priority, stack, APNAP triggers, costs/targets, replacement/continuous effects and state-based actions. Removed/undrawn sources do not confer effects. |
| Combat and interaction | Legal attackers/blockers/tapping, token bodies, commander and poison damage, double/first strike, trample, deathtouch, prevention, indestructibility, interaction windows and recovery after wipes. |
| Win paths and outcomes | Supported combo prerequisites and responses, distinct cast/copy effects, actual opposing wins, elimination, draw and unfinished/censored results; timeouts are never automatic losses. |
| Pilot isolation | Legal actions only; hidden-hand/deck-order permutations cannot affect a pilot with the same observation. Open-decklist experiments are explicitly labeled. No lookahead to future randomness. |
| Symmetry and replay | Browser/Node parity, deterministic replay, same-policy equal-list symmetry after seat rotation, stable accounting and diagnostic failure traces. |
| Support boundary | All four lists and reachable generated cards are assessed at ability/interaction level. Critical unsupported paths block overall outcome recommendations; valid limited diagnostics remain available. |
| Optimization | Zero hard-constraint violations, meaningful candidate substitutions, paired independent random streams, held-out seeds/opponents/policies and selection-bias controls. No retuning against the final holdout. |
| Human comparison | Separate recorded-action replay from prospective decision/outcome prediction. Grouped holdouts by pilot/pod/list family, calibrated uncertainty, cohort failures and baseline comparisons. No universal realism percentage. |

The [simulation plan](simulation-fidelity-plan.md) defines the staged human dataset and proposed metrics. Sample sizes and runtime targets must be justified by pilot variance and measured throughput. A model trained on its own simulations cannot certify agreement with people. No claim of optimal play or globally optimal deck selection is a release requirement.

## Cross-cutting verification

- **Responsive and accessible:** inspect 320/390px phone, 736px intermediate and 1024/1400px desktop layouts; fixed dark mode under both light and dark OS settings, including first paint, native controls and live OS changes. No theme selector or light-mode option. Check keyboard, touch, zoom, forced colors and reduced motion. All tables keep headers, left-aligned columns, sorting/filtering and understandable empty states. Menus/dialogs fit, preserve focus and expose essential options without hover.
- **Local data reliability:** migration from real legacy shapes, uncertain legacy ownership reconciliation, incomplete import batches, quoted CSV names, quantity overflow, unknown prints, Unicode, repeated receipt, database quota, interrupted write, conflicting tabs and corrupt backups. User text is never executable HTML or spreadsheet formulas.
- **Performance:** measure interaction p50/p95, startup, large roster filtering, graph load, worker memory and games/second on named desktop/mobile profiles. Establish budgets from the baseline and user-visible responsiveness; do not invent a full-game throughput promise.
- **Cancellation and stale state:** worker progress is honest; cancellation preserves a compatible checkpoint where supported and never labels a partial result final. Changed deck/facts/rules invalidate stale results.
- **External services:** fixture-backed journeys for determinism plus bounded live smoke checks for supported public lookup/deck import. Exercise timeout, invalid response and CORS fallback. Offline behavior cannot depend on a live service or model response.
- **Independent export checks:** use an XLSX reader independent from the writer and compare exact IDs, quantities, printings, metadata, selected scope and totals. JSON remains the lossless restore format.

## Branch completion procedure

1. At execution start, fetch the public upstream, inspect new handover/PRD/code changes and select the appropriate base. Preserve the approved requirements and current working changes. Work only on feature branches.
2. Implement the milestones in the main plan with focused regression and journey tests. Keep schema migration/rollback, source comments and generated-data manifests with their corresponding change.
3. Bump each changed asset's `?v=` everywhere referenced, then run `node tests/asset-versions.mjs --update` and inspect the diff. Regenerate only affected outputs using their documented inputs/protocol; no manual score edits or bypassing runner budgets.
4. Before **every push**, run `bash runtests.sh -q` and all browser journeys: serve the repo on port 8790, then `node tests/uat/journeys.mjs` with Playwright available. Also pass the relevant new journey, rule, worker, import/export and benchmark checks. Record failures and fixes; skipped checks are not passes.
5. Review the final diff for unrelated changes, accidental user records/keys, inconsistent versions, stale docs and unsupported claims. Prepare screenshots, migration notes, measurement manifests, relevant timings and explicit limitations.
6. Push the feature branch only after the required checks pass. Open or update a **draft pull request**, describing the final behavior and evidence against the correct base. No merge or deployment. Branch completion means implementation, tests, docs and review evidence are ready; it does not mean human calibration is proven without data.
