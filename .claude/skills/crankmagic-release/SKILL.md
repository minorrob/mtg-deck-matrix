# Releasing CrankMagic: checklist → staging → read-back → Linear → production on Rob's go

The rules are `AGENTS.md` ("One release owner", "The production release"), `docs/release-pages.md` and
`docs/release-production.md`. This skill is the procedure and adds nothing to them; where they disagree, they
win and this file is corrected.

**Who releases.** The release owner is the Claude · Engine lane's session. Any other session that is asked to
release stops and says so, unless Rob names it in the conversation. **Production is Rob's go, asked for in the
conversation, every time** — a go for one release is not a go for the next.

**Where.** The staging and production scripts walk the build in a browser and under `wrangler dev`, so they run
where `WRANGLER` (the pinned `wrangler@4.139.0` `bin/wrangler.js`) and a release worktree with `node_modules`
exist: Personal-HP. A cloud container can run steps 1, 3 and 4 (the checklist, the read-back and Linear) and
says plainly that it did not run step 2.

## 1 · The checklist (before anything is built)

| Check | How | Stop if |
| --- | --- | --- |
| `main` is green | the Tests run on `main`'s head (`actions_list(method: list_workflow_runs, resource_id: tests.yml, workflow_runs_filter: {branch: main})`) | the head's run is red or missing |
| Nothing half-merged | open PRs marked ready that touch served files; ask whether to wait | Rob says wait |
| What the release carries | `git log --format='%h %s' <last released main>..origin/main`; the last released main is in the newest commit message on `origin/release/cloud-staging` (`Release <sha> · <date> (cloud-staging): main <full sha>`) | the range is empty: nothing to release |
| Its issues | `git log --format=%s%n%b <range> \| grep -oE 'ROB-[0-9]+' \| sort -u` | — |
| Migrations | `git diff --stat <range> -- cloud/migrations/` | a D1 migration is in the range: it is applied by hand, first, and named in the report |
| Durable Object classes | `git diff <range> -- 'cloud/*worker*.mjs' tools/release-pages.mjs \| grep -nE 'export class\|durable_objects\|new_sqlite_classes\|deleted_classes'` (the Wrangler configuration is generated by the builder, not committed) | any class change: stop and ask Rob (`docs/release-pages.md`, rule 4) |
| Asset versions | `node tests/asset-versions.mjs` | it fails: the `?v=` cascade is stale |
| Secrets | `tools/local-ci.sh origin/main 0` | the scan finds anything |

Write the checklist into the report as you go: each row, its answer, and the command.

## 2 · The staging release (Personal-HP)

```bash
WRANGLER=<wrangler.js> bash tools/release-staging.sh <release checkout> [work dir]
```

Run it as a tracked background task (a shell `&` dies with its shell). It checks out `origin/main` detached,
builds `--profile cloud-staging`, walks the build (`tests/uat/release-acceptance.mjs`, `tests/uat/play-e2e.mjs`),
and only when both pass commits to `release/cloud-staging` and pushes; Workers Builds deploys `crankmagic-staging`
from that branch. `STAGING NOT RELEASED` means nothing was pushed: read the logs in the work dir, file the cause
as an issue, and stop.

## 3 · The read-back (the smoke check)

Staging is behind Cloudflare Access, so it is read as the session's service token, from the environment, never on
a command line or in a file:

```bash
node tools/staging-check.mjs --expect <main sha>
```

It passes when `version.json` names that commit and profile `cloud-staging`, both pages say their version, and
`/api/me` seats the token. Give Workers Builds a minute or two after the push; if the commit is still the old one
after five minutes, report it rather than looping.

- **In a claude.ai cloud container** the proxy supplies the secret as `CF_Access_Client_Secret` (that case), so map
  it for the one command without printing it: `CF_ACCESS_CLIENT_SECRET="$CF_Access_Client_Secret" node tools/staging-check.mjs --expect <sha>`.
  Proven 2026-10-31: exit 0, staging serving `5d8db5b` (cloud-staging) and seating `service:…`.
- **On Personal-HP** the token is `crankmagic-staging-checks-hp`, saved in the Windows user environment; the
  header of `tools/staging-check.mjs` shows how a running session reads it.

Exit 2 means no token in the environment: say so; it is Rob's to provide.

## 4 · Linear: say where each issue is

For each issue key the range carries (step 1), `save_comment(issueId, body: "On staging at <short sha> (release <release commit>, <date>).")`.
An issue that is not Done yet still gets the comment; its status does not change. A key that does not resolve is
listed in the report, not guessed at.

## 5 · Production, only on Rob's go

Ask in the conversation, with the checklist and the staging read-back in front of him: *"Staging is at `<sha>`,
read back. Release `<profile>` to production?"* Without a yes in this conversation, stop here.

On a yes (Personal-HP):

```bash
WRANGLER=<wrangler.js> bash tools/release-production.sh cloud-production <release checkout> [work dir]
git -C <release checkout> push origin release/pages        # the go itself; Workers Builds deploys it
curl -s https://crankmagic.com/version.json                # names this commit and profile
UAT_BASE=https://crankmagic.com UAT_LIVE_NETWORK=1 node tests/uat/release-acceptance.mjs
```

Record the deployed version id (`wrangler deployments list`) as the recovery target. Then each issue the release
carries gets `In production at <short sha> (version <id>, <date>).` Production's rules that never bend: `release/pages`
is written only by `tools/release-pages.mjs --commit` from a commit of `main`; once a release carries the table
class, `pages` is never committed there again (`refuseDropTables`).

## 6 · The report

The release report (in the conversation, and as a comment on the release owner's tracking issue if there is one):
the main commit, the release commit, the checklist table, the walks' counts (acceptance, play-e2e), the read-back
line, the issues commented, and what was not run and why. `AGENTS.md`'s four things apply.

## What this skill never does

- Pushes `release/pages`, or runs `wrangler deploy` against production, without Rob's go in this conversation.
- Releases from a feature branch, the working tree, or a hand-edited build.
- Retries a failed walk until it passes; a failure is a cause to find (`AGENTS.md`, "Failure handling").
- Prints, echoes or writes a token.
